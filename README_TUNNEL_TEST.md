# 실물 터널 테스트 실행

현재 기본값은 **외측 1,820mm·벽 2mm·출입구 300mm 연습장**, `normal`, `start_step=9`다. YAML을 따로 수정할 필요는 없다.

현재 초기 직진의 좌우 판단 범위는 차체 중심에서 **왼쪽 9.03cm / 오른쪽 8.5cm**다. 오른쪽 점군을 본 사용자의 요청으로 오른쪽만 더 좁혔으며, 실측 차체 오른쪽 끝 5.3mm 구간은 이 진입 판단에서 제외된다. 지도와 경로 탐색의 차체 폭·여유는 그대로다.

2026-10-10: 앞선 시험에서 사용자가 **실물 터널 완주를 확인했다.** 현재 초기 직진 상한은 0.30m/s, 경로 순항 상한은 0.32m/s이며 회전 제한은 요청한 Docker FAST 값이다. LiDAR는 **센서 수평면 기준 위아래 ±0.5°·반사 강도 2 이상**인 점을 사용한다. 한 스캔에서 점 1개면 검출로 보고, 같은 칸의 연속 2회 검출로 장애물을 등록한다. 점별 측정 시각 보정과 현재 차체·경로의 1cm 충돌 여유는 유지한다. 최근 두 실패 기록을 이 설정으로 재생했을 때 병 위치 세 영역을 유지하면서 초기·후반의 경로와 출구 연결 검사가 통과했다. **이번 설정의 실제 주행은 아직 미검증이다.** 아래 분석은 각 수정 시점의 검사 결과다.

**PC 전원을 끄는 스위치는 정상 시험 종료에 먼저 사용하지 않는다.** PC를 켜 둔 채 제어기 정지·모터 토크 해제 요청 → 실제 로봇 정지 확인 → 기록 저장을 마친다. 스위치가 모터 전원도 끊는지는 확인되지 않았다.

## 로봇 배치

입구 폭 300mm의 중앙선에 **바퀴축 중앙을 입구 외벽에서 140mm 바깥**에 놓고, 전방을 입구에 수직으로 터널 안쪽을 향하게 한다. 정지한 이 자세가 지도의 원점이 된다. 출구는 들어간 뒤 왼쪽 방향이고, 외벽에서 200mm 바깥의 출구 목표와 연결 구간을 비워 둔다.

## 터미널 1: 센서 시작

```bash
bash scripts/nuc_sensors.sh --mounts
```

카메라·LiDAR·OpenCR와 장착 TF를 실행한다. 터미널을 열어 두고, 기존 `start_robot.sh`나 다른 센서 실행 명령을 함께 쓰지 않는다.

## 터미널 2: 기록 시작

센서 연결 후 실행하고 터미널을 열어 둔다.

```bash
python3 scripts/nuc_trial.py record
```

`Recording: ...`에 시험 폴더가 표시된다. 실제 영상·점군·odom·cmd_vel·motor_power·sensor_state·TF·ROS 로그, 사용 설정·지도·Git 커밋·소스·실행 로그를 보관한다. 기록 크기는 이전 검사에서 약 1.3GB/분이었다.

코드나 설정을 수정한 뒤에는 이전 기록에 이어서 주행하지 않는다. 기존 시험의 정지·기록 저장 순서를 마친 뒤 새 `record`로 시작한다. 시작 검사가 사용 설정·소스와 기록의 일치를 확인한다.

## 터미널 3: 주행 시작

**이 명령을 실행하면 실제 로봇이 주행한다.**

```bash
python3 scripts/nuc_trial.py start
```

약 9초 동안 센서·측정 시각 TF·별도 조종 입력·다른 `/cmd_vel` 발행자·기록 상태를 자동 검사한다. 이어 기존 제어기의 `/cmd_vel` 연결로 0 속도를 보내고, `/motor_power=true` 요청에 대한 새로운 OpenCR `torque=true` 응답을 확인한 뒤 주행을 시작한다. 토크 확인에 실패하면 시작을 중단하고 0 속도·토크 해제를 요청한다. 그동안 로봇을 옮기지 않는다. `/tb_controller`는 `normal`, step 9, 연습용 설정, PointCloud2로 시작한다. 현재 YAML의 진입 상한은 0.30m/s, 터널 순항 상한은 0.32m/s다.

속도는 `codes/stepbystep/tunnel.real.yaml`의 다음 항목으로 조절한다. 별도 실행 인자는 필요 없다.

| 인자 | 현재 값 | 적용 구간 |
| --- | --- | --- |
| `control.cruise_velocity` | 0.32m/s | 계획 경로 순항 상한 |
| `entry.cruise_velocity` | 0.30m/s | 최초 직진 진입 상한 |
| `control.entry_velocity` | 0.04m/s | 진입·계획 경로의 시작 속도 기준 |
| `control.exit_velocity` | 0.025m/s | 계획 경로 끝의 속도 기준 |
| `control.maximum_angular_velocity` | 1.4rad/s | 좌·우회전 각속도 상한, FAST 값 |
| `control.maximum_lateral_acceleration` | 0.30m/s² | 커브 속도를 제한하는 횡가속 상한, FAST 값 |
| `control.angular_acceleration` | 8.0rad/s² | 회전 속도 변화율 상한, FAST 값 |

실물 `normal` 설정에 위 회전 관련 세 항목을 반영했다. 초기 직진은 사용자 요청에 따라 `entry.cruise_velocity`를 **0.30m/s**로 높였다. `control.cruise_velocity`는 초기 직진 상한을 바꾸지 않는다. 출구 속도, 직선 가감속과 추종 게인은 유지했다. 커브와 목표까지 남은 거리에 따라 감속하므로 상한이 항상 실제 주행 속도가 되는 것은 아니다.

**장애물 검사는 거리·경로 기준이다.** 현재 차체와 남은 계획 경로에 `footprint.padding: 0.010`의 1cm 여유를 적용한다. 현재 차체가 장애물과 겹치면 정지하고, 남은 경로가 막히면 정지 후 다시 탐색한다. 속도·각속도로 미래 정지 궤적을 계산하는 검사와 정지 뒤 정면 1cm를 추가로 이동시키는 검사는 제거했다. 속도별 제동거리를 미리 검사하지 않으므로 이 변경이 실제 제동 성능을 검증한 것은 아니다. 초기 직진은 기존대로 최대 92cm 또는 앞범퍼 기준 장애물 여유 30cm에서 끝난다. 센서 시각·TF 검사도 유지한다.

실행 스크립트는 순항·진입 속도가 유한한 양수인지 검사하며 별도의 숫자 상한을 두지 않는다. 속도 값은 YAML 본문의 숫자가 기준이다. YAML 값을 변경한 뒤에는 새 `record`로 변경된 설정을 기록하고 기존 `start` 명령을 사용한다. 이번 회전 설정 변경도 새 기록부터 적용한다.

**터널 완료 후 step 11 차선 주행으로 계속 이어진다.** 자동 종료가 아니며 이후 속도는 터널 normal 설정으로 제한되지 않는다. 완주 확인과 별개로 실제 odom 거리 스케일·제동 성능은 정량 검증하지 않았다.

## 터미널 4: 로봇 정지 → 기록 저장

PC와 센서는 켜 둔 상태로 실행한다.

```bash
python3 scripts/nuc_trial.py stop
```

이 명령은 `/tb_controller`를 종료하고 기존 OpenCR의 `/motor_power`에 false를 보내 토크 해제를 요청한다. 새 `/sensor_state` 응답의 `torque=false`를 확인해 결과를 출력한다. 이 값은 드라이버가 보고한 상태이며 실제 바퀴 정지나 기계식 브레이크를 입증하지 않는다. **로봇이 실제로 멈췄는지 확인한 뒤** 다음을 실행한다.

```bash
python3 scripts/nuc_trial.py stop-record
```

**`Bag finalized: .../sensors.bag`가 나오면 기록 파일의 정상 종료가 완료된 것이다.** 그다음 터미널 1에서 Ctrl+C로 센서를 종료하고, PC는 운영체제의 정상 종료로 끈다. 즉시 전원을 끊는 스위치는 파일 시스템 손상을 피하려면 운영체제 종료 후 사용한다.

정지 명령이 실패하거나 로봇이 계속 움직이면 실제 구동 전원을 차단해야 한다. PC 전원 차단만으로 로봇 정지를 보장하지 않는다. `/step=0`이나 한 번의 zero `/cmd_vel`도 지속 정지 방법이 아니다. 주행 터미널의 Ctrl+C는 제어기를 종료하므로 이후에도 위 `stop`과 기록 종료 순서를 따른다.

다음 시험은 시작 위치에 배치하고 새 `record` 후 같은 `start`를 실행한다. `start`가 모터 토크를 다시 활성화하므로 별도 토크 명령은 필요 없다. 현재 펌웨어 watchdog과 실제 제동 성능은 별도로 검증하지 않았다.

## 기록 위치와 오류 확인

기록은 `records/날짜_시각_마이크로초_KST/`에 저장된다. 최신 시험 확인:

```bash
TB_TRIAL_DIR=$(cat records/current_trial.txt)
rosbag info "$TB_TRIAL_DIR/sensors.bag"
tail -n 30 "$TB_TRIAL_DIR/controller.log"
```

시작 전 센서 오류는 같은 폴더의 `prestart_diagnostics.json`과 로그, 기록 오류는 `rosbag.log`를 확인한다. 종료 후 `.bag.active`가 남으면 정상 종료된 것이 아니므로 파일을 보존한다. 내부 state/reason은 로그에 있지만 계획 경로·costmap 전체가 자동 저장되는 것은 아니다.

`records/20261010_021011_617357_KST/`에는 0이 아닌 `/cmd_vel` 472개가 있지만 `/sensor_state.torque`는 전부 false이고 바퀴 엔코더도 사실상 변하지 않았다. 기존 `stop`은 토크를 해제하는데 `start`에 복구 절차가 빠져 있었다. 위 시작 절차에 토크 활성화·응답 확인을 추가했다. 새 기록부터 `/motor_power` 요청도 함께 저장한다.

수정 후 전체 단위 테스트는 136개 중 135개 통과했다. 기존 게이트 전환의 `8.5`/`9` 불일치 1개는 그대로이며 새 토크 활성화·시작/정지 검사는 통과했다. 결과는 같은 분석 폴더의 `final_unit_tests.log`에 있다.

## Windows에서 RViz 보기

Windows의 [MobaXterm](https://mobaxterm.mobatek.net/download-home-edition.html)에서 **Session → SSH**로 접속한다. 현재 NUC 주소는 `192.168.0.3`, 사용자 이름은 `sj`다. **Advanced SSH settings → X11-Forwarding**을 켜고 새로 연결한다. 센서가 이미 켜져 있으면 다시 시작하지 않는다.

새 터미널에서 폴더 이동:

```bash
cd /home/sj/ParkCars/TB-tunnel-nuc
```

화면 연결 확인 후 실행:

```bash
echo "$DISPLAY"
bash scripts/nuc_rviz.sh
```

`DISPLAY`는 `localhost:10.0`처럼 표시되어야 한다. `:0`이면 NUC의 모니터를 가리키므로 MobaXterm의 X11 전달 설정을 확인하고 재접속한다. NUC의 `.bashrc`는 SSH가 지정한 화면 주소를 보존하도록 수정했다. `DISPLAY=:0`을 수동으로 설정하지 않는다. 설정 근거: [MobaXterm 공식 X11·SSH 안내](https://mobaxterm.mobatek.net/documentation.html).

RViz는 `odom` 좌표계에 `/livox/lidar` 점군·TF·`/odom`과 `/camera/color/image_raw` 영상을 표시한다. 위에서 보는 화면으로 시작하며 점의 색은 높이다. `Views`에서 `Orbit`을 선택하면 옆에서도 볼 수 있다. 센서 보기만 실행하며 제어기나 이동 명령을 시작하지 않는다. 종료는 창 닫기 또는 해당 터미널의 Ctrl+C다.

계획 경로와 costmap은 현재 제어기가 RViz 토픽으로 발행하지 않으므로 이 화면에는 표시되지 않는다. 원격 화면의 프레임 속도는 SSH와 그래픽 처리 속도의 영향을 받으며 센서 수신 Hz와 다르다. NUC의 임시 가상 화면에서 실제 영상·점군 표시와 TF 연결을 확인했다(`records/rviz_sensor_view.png`). Windows 쪽 실제 창 표시는 해당 PC에서 연결 후 확인해야 한다.

## 2026-10-10 첫 기록에서 확인한 planning 실패

기록의 카메라 약 30Hz·LiDAR 10Hz·odom 약 29Hz는 정상이며, 시도 중 `/cmd_vel`은 모두 0이었다. 입구 중앙의 높이 약 23~30cm 점들이 이전 높이 필터에 포함되어 바닥 장애물로 투영되고, 전방 여유가 약 9cm로 계산되어 길을 막았다. 사용자가 확인한 문틀 아래 높이는 **250mm**, 차체 바로 뒤 왼쪽 케이블 높이는 **약 175mm**다. 시트와 부품 사양에서 계산한 최고 부분은 LiDAR 상단 약 205mm다.

당시 연습용 높이 상한을 **220mm**로 조정해 로봇보다 약 15mm 높은 부분까지 감지하면서 입구 위쪽 점을 제외했다. 이후 수평각 필터가 이 높이 필터를 대체했고, 현재는 아래의 ±0.5°·강도 2 이상 설정을 사용한다. 이전 기록을 재생해 계획 경로와 출구 연결 통과를 확인했다. 해당 검사 시점에 실제 로봇의 통과·주행·제동은 아직 검증되지 않았다. 높이 계산 근거는 `NUC_MEASUREMENTS.md`에 있으며, 점군의 약 230mm와 문틀 250mm의 차이는 독립 실측으로 해결된 것이 아니다.

점군상 시작 위치는 지도의 기준보다 약 9~10cm 더 바깥으로 추정된다. 다음 배치 때 앞 범퍼가 아닌 **바퀴축 중앙에서 입구 외벽까지 140mm**를 맞춘다. 자동 지도 정합은 없다.

점군의 불필요한 재직렬화를 제거하고 수신 버퍼를 조정했으며, 사용하지 않는 지도 재계산과 반복되는 격자 범위 검사 비용을 줄였다. 원본 좌표·필터 계산의 동등성을 검사했고, 탐색·충돌 계산식·추종 게인·시간 제한은 바꾸지 않았다.

## 현재 병 연습: 라이다 수평면으로 장애물 판단

현재는 `sensors.horizontal_half_angle_deg: 0.5`, `sensors.minimum_intensity: 2`, `grid.mark_observations: 2`이다. **원본 LiDAR 수평면에서 위아래 ±0.5° 이내이며 반사 강도가 2 이상인 점**을 선택한 다음 장착 TF와 점별 이동 보정을 적용한다. 기존 Livox 입자 태그 필터도 유지한다. `z_min`·`z_max`는 수평각 옵션이 있을 때 사용하지 않으며, 그 옵션을 제거하면 기존 높이 필터로 돌아간다. 강도 필터는 기본값 0에서 꺼지고, 양수로 켠 상태에서 강도 필드가 없거나 잘못되면 점군 갱신을 거부한다.

### 직진 속도와 남아 있는 근접점

다음 `records/20261010_041023_870353_KST/` 시험은 폭 180.6mm 설정으로 6.25초 동안 약 232mm 직진했다. 명령 속도는 최대 0.04m/s, odom 속도 중앙값은 약 0.0388m/s였다. 느린 직진을 개선하려고 `entry.cruise_velocity`만 **0.04 → 0.10m/s**로 높였다. 기존 가속 0.15m/s²와 감속·정지 간격을 유지한다. 최신 기록과 비교해 이 값만 바뀌었고 실행 스크립트의 설정 검사를 통과했다. 속도 상향 후 실제 주행은 아직 미검증이다.

이 시험의 직진 종료는 920mm 거리 도달 때문이 아니다. 센서 높이보다 약 1mm 위, 차체 중심에서 오른쪽 약 87.6mm인 한 점 때문에 앞 간격이 약 94mm로 계산됐다. 이번에는 실측 차폭 안이므로 앞서 줄인 폭에도 포함된다. 다음 점군에서는 그 가까운 점이 사라졌지만, 이후 같은 위치 부근의 점이 다시 관측됐다. 현재 로직은 근접점으로 감속해 명령 속도가 0이 되면 ENTRY를 끝내므로, 짧게 나타난 점으로도 planning에 전환될 수 있다. 물체나 반사의 정체는 아직 확정되지 않았다. 속도 상향이 이 근접점 문제까지 해결한 것은 아니며, 판단 폭·강도 필터·직진 종료 조건을 추가로 바꾸지 않았다.

분석 자료·종료 순간 카메라 영상은 `records/analysis_20261010_041023_entry/`에 있다. 변경된 속도는 새 `record` 후 기존 `start`로 적용한다.

### 그림 확인 후 오른쪽 판단 폭만 추가 축소

사용자가 오른쪽 점군을 보고 오른쪽만 조금 줄이도록 요청했다. 현재 `entry.obstacle_half_width: 0.0903`은 왼쪽에 유지하고, `entry.obstacle_right_width: 0.085`로 오른쪽만 5.3mm 줄였다. 전체 진입 판단 폭은 175.3mm다. 오른쪽 옵션을 생략하면 다시 좌우 대칭인 `obstacle_half_width`를 사용한다. 수평 ±1°와 앞 30cm 간격, 속도와 지도·경로 충돌 계산은 이 폭 변경으로 조정하지 않았다. 오른쪽 벽 점은 센서 화면과 지도에 계속 남지만 새 범위 밖의 점은 초기 직진 종료 근거에서 빠진다.

같은 기록의 초기 직진 점군 62개에서는 조기 종료 조건이 1개에서 0개로 줄었다. 문제 점군의 앞 간격은 9.36cm에서 66.25cm로 바뀌었다. 이후 2초를 포함한 82개 점군에서도 새 폭 안의 조기 종료 조건은 없었다. 이 결과는 기록 재생이며 새 설정으로 92cm 직진하거나 실제 물체를 피한 주행 검증은 아니다. 근거는 같은 분석 폴더의 `right_width_comparison.json`이다. 새 기록부터 주행한다. RViz는 원본 점군을 보여주므로 변경된 진입 판정 폭이 별도로 표시되지는 않는다.

## 2026-10-10 수평 0mm 단면과 1회 검출 시험 이력

`records/20261010_044602_794739_KST/`에서는 출구 중앙 근처의 점이 위쪽 약 0.9°로 들어와 장애물 칸이 됐다. 약 22cm라는 값은 수평 장착 TF를 가정한 환산 높이이며 실제 바닥 높이 실측이 아니다. 영상 투영과 IMU 가속도에는 출구 상부 판일 가능성을 뒷받침하는 단서가 있으나 표면을 확정하지 않았다. 마지막 검출 이후에도 삭제에 필요한 연속 관측이 부족해 약 11초 동안 칸이 남았다.

## 2026-10-10 05:03 시험: 점 개수와 검출 횟수 정정

`records/20261010_050343_460454_KST/`에서는 91.3cm 직진 후 내부 경로를 찾았으나 출구 연결이 충돌 검사에 걸렸다. 기록 재생에서 원인은 직진 중 **한 번만 들어온 원본 `z=0` 점 하나**가 출구 왼쪽 안쪽의 장애물 칸으로 남은 것이었다. 이 점은 지도상 출구 평면보다 약 6.7cm 안쪽이며 실제 어떤 표면에서 생겼는지는 미확정이다. 이후 같은 칸의 추가 검출이나 지우는 관측이 없어 1회 등록 설정에서 계속 남았다.

기존 코드의 점 개수 기준은 이미 **스캔당 한 칸에 유효 점 1개**다. `mark_observations`는 점 개수가 아니라 연속 스캔 횟수이며, 사용자 요청을 잘못 해석해 바꾼 1회 설정을 기존 2회로 되돌렸다. 같은 기록의 2회 재생에서는 문제 칸이 등록되지 않고 초기·후반의 새 경로와 출구 연결이 통과했다. 이는 해당 정지 원인에 대한 재생 검증이며, 원본 `z=0`만 선택할 때 병의 검출이 드물어지는 문제까지 해결한 것은 아니다. 이번 기록의 기존 세 병 위치 주변을 비교해도 2회 설정의 초기 장애물 칸이 모두 0개였고, 그 초기 경로는 1회 설정의 더 많은 관측을 담은 지도에서 충돌했다. 병 배치가 이전과 동일한지는 미확정이지만, 원복 후 경로 생성 성공만으로 주행 준비 완료라 할 수 없다. 현재 조합의 실제 주행은 미검증이다.

계획 중에도 LiDAR 약 10Hz, odom 약 29Hz, 카메라 약 30Hz가 기록됐으며 처리한 262개 점군 모두 유효 스캔을 만들었다. `waiting for fresh`는 일시적 신선도 검사 실패 뒤 센서가 회복돼도 계획 worker가 실행 중이면 문구가 남을 수 있어, 반복 로그 전체를 센서 단절 시간으로 해석하지 않는다. 제어기 내부 지연의 정확한 원인은 기록만으로 확정하지 않았다. 시간 제한이나 센서·경로 코드는 이번 정정에서 바꾸지 않았다.

근거: `records/analysis_20261010_050343/`의 `exit_measurement_trace.json`, `route_collision_details.json`, `mark_two/replayed_plans.json`과 `records/analysis_20261010_050343_fresh/summary.json`. 설정 검사와 YAML 비교로 이번 실행 설정 변경은 `mark_observations: 1 → 2`뿐임을 확인했다.

추가 비교에서 ±0.3°·연속 2회도 최신 05:03 기록의 초기 병 위치 영역 세 곳 중 한 곳을 확정하지 못했다(확정 칸 5/21/0개, 후반 4/22/3개). 출구 경로 생성 자체는 성공했으나 초기 내부 경로가 나중에 등록되는 관측 칸과 겹쳤다. 따라서 앞선 04:46 기록에서의 ±0.3° 성공을 이번 시험의 해결 근거로 확대하지 않으며, 운영 각도는 이번 비교에서 변경하지 않았다.
