# 전체 주행 안내

준비·센서 실행·전체 주행·종료 순서는 [README.md](README.md)를 참고한다.

## 터널 V1 / V2 선택

기본값은 기존 V1이다. `mission.py`, `planner.py`, `tracking.py`의 기존 구현은 V1로 보존한다.
V2는 `mission_v2.py`를 통해 선택하며 같은 센서 입력과 하나의 `/cmd_vel` 발행자를 사용한다.

센서를 준비한 뒤 기존 주행 명령에 버전만 지정한다. 시작 단계는 실행 파일의 기존 설정을 따른다.

```bash
TB_TUNNEL_VERSION=v1 python3 codes/stepbystep/try_maze.py
TB_TUNNEL_VERSION=v2 python3 codes/stepbystep/try_maze.py
```

`codes/stepbystep/faster_2.py`와 `codes/final_codes/try_maze.py`도 같은 선택을 지원한다.
ROS private parameter `_tunnel_version:=v1` 또는 `_tunnel_version:=v2`가 환경 변수보다 우선한다.
시작 로그의 `Tunnel version:`에서 실제 선택을 확인한다.

기록 도구의 기존 `start`, `start0`, `start8` 명령에도 `TB_TUNNEL_VERSION=v2`를 지정할 수 있다.
`trial.json`과 컨트롤러 명령에 버전을 기록한다. 버전을 지정하지 않으면 V1을 사용한다.

### 실차 터널 단독 V2 실행

NUC의 `/home/sj/Desktop/TB`에서 `codex/tunnel-gazebo` 브랜치를 업데이트한다.

```bash
cd /home/sj/Desktop/TB
git fetch origin
git switch codex/tunnel-gazebo
git pull --ff-only
```

로봇을 기존 연습 터널 진입 위치에 놓는다. 첫 번째 터미널에서 센서를 실행하고 유지한다.
이미 센서가 실행 중이면 중복 실행하지 않는다.

```bash
cd /home/sj/Desktop/TB
bash scripts/nuc_sensors.sh --mounts --depth
```

두 번째 터미널에서 실차 환경을 불러오고 기록을 시작한다. 기록 터미널은 열어 둔다.

```bash
cd /home/sj/Desktop/TB
source scripts/nuc_env.sh
python3 scripts/nuc_trial.py record
```

세 번째 터미널에서 V2로 주행한다. `start`는 터널 단독 STEP 9이며,
센서·TF·기록·명령 발행자 확인 후 모터 토크를 활성화한다.

```bash
cd /home/sj/Desktop/TB
source scripts/nuc_env.sh
TB_TUNNEL_VERSION=v2 python3 scripts/nuc_trial.py start
```

`tunnel.real.yaml`의 연습장 지도와 실물 보정을 그대로 사용한다. 이 파일의 `normal`은
현재 진입 0.25m/s·주행 0.32m/s이며, 저속 모드라는 뜻이 아니다. 시작 로그에서
`Tunnel version: v2`와 `tunnel.real.yaml`을 확인한다. V1 비교는 위 시작 명령의 `v2`를
`v1`로 바꾸고 같은 위치·장애물 배치에서 새 기록을 시작한다.

터널 이후에는 STEP 11 차선 주행이 계속된다. 주행 터미널에서 `Ctrl+C` 후 정지하고,
실제 정지를 확인한 뒤 기록을 마무리한다.

```bash
python3 scripts/nuc_trial.py stop
python3 scripts/nuc_trial.py stop-record
```

`Bag finalized`를 확인한 뒤 센서 터미널을 종료한다. 기록은 `records/`에 저장된다.

### 구현과 검증

V1/V2 비교에는 같은 `tunnel_config`, 속도 profile, 장애물 배치와 시작 자세를 사용한다.
기존 `tunnel.yaml`·`tunnel.real.yaml`의 지도·차체·센서·실물 보정은 공유하고,
V2에만 필요한 설정은 각 패키지의 `tunnel/v2.yaml`에서 읽는다.
`config['v2']`가 있으면 해당 항목만 덮어쓴다.

V2는 참조 코드의 `pathplan → 가까운 목표 선택 → get_velocity_maze` 흐름을 따른다.
전역 단계는 현재 위치에서 출구까지 방향 차원 없이 2D A* 경로를 만든다. 지역 단계는 매
제어 주기 현재 위치와 방향에서 짧은 원호 후보를 평가하고, 가까운 전역 목표로 향하는
명령을 선택한다. V2에는 Hybrid A* 지역 탐색이나 고정된 경로 끝점 이어 붙이기가 없다.
V1의 계획기는 V2에서 기존 차체·회전반경·충돌 검사 기능만 제공한다.

전역 갱신은 별도 작업에서 수행한다. 새 결과가 아직 없거나 경로 계산에 실패해도 기존
전역 안내를 유지하고 현재 지도에서 지역 명령을 계속 검사한다. 갱신 자체가 정지나 속도
초기화를 일으키지 않는다. 실제 차체가 막히거나 제동 여유가 없거나 입력이 오래되면
정지한다. 참조 코드의 작은 중심점 여유나 검사 없는 제자리 회전은 그대로 복사하지 않았다.
기존 직사각형 차체와 여유 폭으로 실제 제한된 명령 및 반응·제동 구간을 검사한다.

`replan_period`는 전역 갱신 간격, `local_lookahead`는 가까운 목표 거리,
`local_horizon`은 원호 평가 거리다. 실제 제동에 더 긴 거리가 필요하면 그 거리도 검사한다.
V1 파일과 실물·시뮬레이션 보정은 변경하지 않았고, 실행 중 V1/V2 자동 전환은 하지 않는다.

종료 인계도 각 실행 파일의 기존 동작을 따른다. `stepbystep`은 목표에서 측정된 정지를
확인하고, `final_codes`는 출구 차선 확인을 기다린다. 두 폴더 사이의 비교가 아니라
같은 실행 파일에서 버전만 바꿔 비교한다.

Gazebo 선택 명령은 [DOCKER_NOETIC.md](DOCKER_NOETIC.md)를 참고한다.
단위 검사와 터널 직전 시작 시험은 전체 코스 검증과 구분한다. 아래 결과는 터널 단독
Gazebo 시험이며, 공식 시작점 통합 주행과 실물 반복 성능은 검증하지 않았다.

참조 구조로 수정한 뒤의 [현재 검증 기록](tests/validation_reference_v2_20261026.json)은
같은 FAST·A 배치·시작 자세에서 ROS/Gazebo를 매번 새로 실행한 결과다.

| 버전 | 출구 정지·STEP 11 인계까지 | 첫 계획 정지 | 주행 중 0 선속도 명령 |
| --- | --- | --- | --- |
| V1 | 16.975 / 16.963초, 2회 통과 | 0.918~1.089초 | 0회 |
| 수정 V2 | 12.467 / 12.408 / 12.461초, 3회 통과 | 0.202~0.252초 | 0회 |

시간은 첫 양의 전진 명령부터 첫 STEP 11 로그까지의 시뮬레이션 시간이다. 최고 전진 명령은
두 버전 모두 0.32m/s, 횡가속 상한도 동일한 0.30m/s²다. 평균은 16.969→12.445초로
약 4.524초(26.7%) 줄었다. 초기 계획 대기 감소와 주행 중 높은 속도 유지가 함께 기여했다.
이 수치를 전역 탐색 계산 시간만의 개선으로 해석하지 않는다.

V2는 주행 중 전역 경로를 24~25회 갱신했고 갱신으로 인한 중간 정지는 없었다. 기존 진입
정지와 목표 정지는 유지한다. 세 번 모두 목표의 측정 정지 후 차선 제어로 4초 이상,
약 0.414~0.418m 이동했다. 표본 차체 형상 검사에서 벽·원통과의 겹침은 0건이었다.
접촉 센서 기반 연속 충돌 증명이나 B/C 배치 검증은 아니다. 별도 개발 1회(12.448초)는
평균에 넣지 않고 보존했다. Noetic 컨테이너의 관련 단위 검사 41개도 통과했다.

아래 기록은 참조 구조로 다시 수정하기 전 V2에 대한 보존 기록이다.

2026-10-26 정적 지도 비교에서는 세 시작 자세의 V2 첫 구간이 0.087~0.092초에 나왔다.
V1 전체 계획은 0.499~1.655초였다. 다만 V2 전체 계획 시간은 0.505~2.693초로,
전체 계산량 감소는 확인하지 못했고 한 조건에서는 증가했다. 확인된 차이는 첫 경로의
준비 시점이며 이후 계산을 주행과 겹칠 여지가 있다는 것이다.
조건·경로 검사·기각한 초기 설계는 [정적 검증 기록](tests/validation_v2_static_20261026.json)에 있다.
이는 동적 장애물·센서 재생·실시간 제어·실물 반복 주행 결과가 아니다.

2026-10-26 실제 Gazebo 확인 결과는 [주행 검증 기록](tests/validation_v2_gazebo_20261026.json)에 있다.
`layout_a`의 V2 `normal` 터널 직전 시작 1회는 출구 도달·측정 정지·STEP 11 차선 제어
복귀까지 72.14초였고, 이후 4초 동안 0.411m 이동했다. 첫 경로 준비 정지는 0.366초였다.
경로 추종 중 목표 정지 이전의 정확한 0 속도 명령은 없었지만, 0.032초의 매우 낮은 양의
속도 명령은 관측했다. 명목 차체 외곽의 표본 검사에서는 벽·원통과의 겹침이 없었다.
`fast`는 지역 경로 확보 실패·경로 절단 후 정지했고, 추종 오차 초과 상태로 종료해 미통과다.
공식 시작점 시험은 초록 신호와 1~5단계를 거쳤으나 앞선 장애물 구간에서 진행하지 못해
터널에 도달하지 못했다. 따라서 V2의 공식 통합 주행·반복 안정성 검증 완료를 뜻하지 않는다.
시험 중 발견한 동명 실행 파일 선택 문제는 고유 심볼릭 링크로 수정했다. Gazebo는
`scripts/tb_tunnel_controller.py`를 통해 기존 `codes/stepbystep/try_maze.py` 하나를 실행한다.

현재 개발 시험은 사용자 요청에 따라 터널 직전 단독 출발로 한정한다.
같은 FAST·시작점·배치·센서·기록 조건에서 버전만 바꾼 [추가 비교](tests/validation_fast_comparison_20261026.json)는
V1이 17.113초와 16.820초로 2회 통과했고, V2는 첫 이동 후 86.167초까지 완료하지 못했다.
V2의 첫 계획 정지는 0.416초로 V1의 0.966~0.974초보다 짧았지만, 후속 경로를 얻지 못해
주행 중 정확한 0 속도 명령이 합계 75.898초 발생했다. 따라서 완료시간 단축으로 볼 수 없다.
반환 이유·경로를 기록한 별도 V2 계측 실행 2회는 16.800초와 16.978초로 통과했다.
계측은 실행 타이밍에 영향을 주므로 위 성능 비교에 합치지 않는다. 실패 실행의 세부 탐색
종료 이유는 기존 로그에 없고 계측 실행에서 재현되지 않아 아직 특정하지 못했다.
수정 전 V2는 짧은 안전 경로의 끝에서 출구까지 연결 가능한지 보장하지 않으며,
연결 실패 시 같은 끝 자세를 기준으로 다시 탐색하다 남은 경로를 소진하면 정지한다.
기존 FAST의 18.777~20.140초 통과 기록은 보존하고, 현재 비교 기준은 V1 FAST로 둔다.
